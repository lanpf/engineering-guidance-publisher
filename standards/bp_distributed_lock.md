# 分布式锁最佳实践

本文基于 `framework-lock` 和 `framework-starter-lock-redis`，定义跨进程互斥、锁键、超时和数据一致性约束。

## 分布式锁

- 对数据并发写入，不得依赖数据库行锁、表锁或“先查询再写入”作为跨实例协调手段；使用分布式锁串行化竞争，并以数据库唯一索引或等价约束作为最终一致性防线。
- 分布式锁不得作为唯一正确性保证。写操作必须同时具备幂等性、唯一约束或乐观并发控制，并正确处理锁过期、进程暂停、网络分区和重复执行。
- 统一注入 `LockExecutor`，通过 `LockContext(scene, key, waitTime)` 执行临界区；业务代码不得直接依赖 Redisson、Spring Integration Redis Lock 或自行操作 Redis 锁命令。
- `scene` 必须是稳定、低基数的业务场景名，`key` 必须是同一竞争资源的规范化业务唯一键；不得包含敏感数据，不得使用随机值，也不得让同一资源出现多种键格式。
- 使用全局 namespace 隔离环境和应用；不得在业务代码手工重复拼接应用或环境前缀。
- 等待时间必须有界并按业务 SLA 配置，默认优先立即尝试；获取失败必须返回明确的可重试、冲突或降级结果，不得无限等待或在循环中无退避抢锁。
- 租约必须覆盖正常临界区上界并留出安全余量；启用自动续租时仍须限制临界区时长。临界区应只包含必要的读改写，不执行可避免的远程调用、大批量处理或长事务。
- 只允许持有锁的执行流在 `finally` 中解锁；必须使用 `LockExecutor` 的托管执行保证释放，不得跨线程移交锁所有权。
- 多把锁必须定义并统一获取顺序；能通过一个聚合或业务唯一键收敛时不得获取多把锁，避免死锁和锁粒度扩大。

## 验证

- 集成测试必须使用真实 Redis 覆盖互斥、获取失败、异常释放、租约/续租和 namespace 隔离。
- 并发写测试必须同时证明只有一个业务结果生效且数据库唯一约束可阻止绕过锁的重复写入。
