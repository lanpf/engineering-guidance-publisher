# 服务错误码最佳实践

本文定义服务错误码的结构、分段、文档和发布稳定性约束。

## 错误码

- **强制 · 主题**：完整错误码固定为 6 位：3 位服务前缀加 3 位本地码；错误枚举只声明本地码，由框架补零并组合完整码。
- **强制 · 主题**：一个服务工程代表一个限界上下文并使用唯一服务前缀；独立部署的限界上下文必须使用不同前缀。
- **强制 · 主题**：服务前缀必须在部署体系内统一登记分配后使用；同一部署体系内不同服务不得使用相同前缀。
- **强制 · 主题**：错误码各类别必须按下表使用对应码段、名称前缀与语义。

| 类别 | 本地码段 | 名称前缀与语义 |
| --- | --- |
| 公共领域错误 | `000-099` | `DOMAIN_`，公共领域有效性与规则 |
| 聚合领域错误 | `100-599` | 聚合名，所属聚合的领域规则 |
| 应用错误 | `600-699` | `APP_`，应用用例错误 |
| 自有技术机制错误 | `700-799` | `INFRA_TECH_`，持久化、缓存、锁、序列化、文件、事件存储及 outbox 等 |
| 外部集成适配错误 | `800-899` | `INFRA_ACL_`，外部集成适配边界失败 |
| 保留 | `900-999` | 不得分配 |

公共及聚合领域错误使用 `DomainError`，应用错误使用 `ApplicationError`，技术机制与外部集成适配错误使用 `InfrastructureError`。ACL 表示防腐职责，不要求建立独立命名的 module。

- **强制 · 主题**：聚合码块以对齐的 50 个码位为最小分配单位，例如 100–149、150–199、…、550–599；聚合可以独占一个或多个连续完整码块，码块不得拆分、共享或重新分配。

- **强制 · 主题**：外部拒绝若具有稳定的本地业务语义，必须转换成 `DomainError` 或 `ApplicationError`，不得仅因来自外部系统就归类为基础设施错误。

- **强制 · 主题**：公共领域错误的 `000` 固定为 `DOMAIN_ENTITY_ID_INVALID`；公共错误前缀遵循本节分类表。
- **强制 · 主题**：每个聚合分配范围的前两个本地码固定为 `{AGGREGATE}_NOT_FOUND`、`{AGGREGATE}_ALREADY_EXISTS`；名称前缀遵循本节分类表。
- **强制 · 主题**：错误枚举声明在拥有该错误语义的 module：领域错误枚举在 domain，应用错误枚举在 application，基础设施错误枚举在对应 infrastructure module；适配器转换并抛出领域或应用异常，不改变其错误枚举的语义归属。
- **强制 · 主题**：错误枚举按所属聚合、技术机制或公共领域码段划分并对应命名，不建跨层混用的单一枚举。
- **强制 · 主题**：完整错误码在同一部署体系内必须全局唯一；本地码只需在所属服务前缀内唯一。
- **强制 · 主题**：每个服务自定义错误码必须绑定唯一、稳定的错误信息模板；异常抛出点不得覆盖模板、拼接临时文案或传入任意 message。确需动态上下文时，只能填充模板预先声明的参数，且不得改变错误语义。框架通用技术断言码的可定制诊断消息不是业务消息模板，其使用边界遵循[校验与异常最佳实践](bp_validation.md#显式检查)。
- **强制 · 主题**：具有稳定错误码的业务错误信息模板统一使用中文；Bean Validation 和技术前置条件的诊断 message 遵循[校验与异常最佳实践](bp_validation.md#异常与消息)。
- **强制 · 主题**：权威领域文档必须记录服务前缀、公共领域码段及每个聚合占用的完整码块。
- **强制 · 主题**：未分配的完整码块可用于扩容，已分配码块中的空码仍归原聚合。
- **强制 · 主题**：新错误按所属码段的本地码顺序追加。
- **强制 · 主题**：已发布错误码不得修改、复用或分配给其他语义。
