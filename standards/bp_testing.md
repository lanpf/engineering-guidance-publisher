# Java 测试最佳实践

本文定义单元测试、模块契约测试和集成测试的边界、结构及验证约束。

## 测试边界

- 单元测试和模块内契约测试放在被测 module 的 `src/test`，就近验证类行为、模块协作和配置边界。
- 跨 module、完整自动装配或依赖真实数据库、中间件的场景属于集成测试，不得放入生产 module。

- 服务工程的独立集成测试 module 及其依赖边界遵循[服务分层最佳实践](bp_layered_service.md#模块职责)。
- 测试必须验证可观察行为和公共契约，不依赖非必要实现细节；真实基础设施优先使用 Testcontainers 获得隔离且可重复的环境。
- 单元测试只能 Mock 被测对象注入的外部协作对象；不得对被测对象本身使用 partial mock 或 spy 替换被测逻辑。

## 结构与生命周期

- 集成测试场景保持自包含，容器、测试应用、配置、探针和生命周期管理优先放入对应 `*IT`。
- 仅在多个测试存在稳定且有意义的复用时抽取测试支持，不得仅为减少少量重复建立通用基类。
- 单元测试和模块契约测试命名为 `*Test`，由 Maven Surefire 在 `test` 阶段执行。
- 集成测试命名为 `*IT`，由 Maven Failsafe 在 `integration-test` 和 `verify` 阶段执行。
- 测试方法使用 `should<ExpectedBehavior>` 命名，直接描述被验证的可观察行为。
- 外部基础设施优先通过 `@Testcontainers` 和 `@Container` 管理；测试创建的应用上下文和执行器必须在 `@AfterEach` 释放。

## 文档与观测

- 每个集成测试必须有同名文档，包含目标、条件、执行方式、手工观测步骤、观察入口和预期结果。
- 独立测试 module 的根 `README.md` 只保留覆盖范围、环境要求、统一执行、报告位置和文档索引；详细场景放在 `docs/<测试类名>.md`。
- 集成测试必须允许手工观察关键过程和最终结果；仅有自动断言或源码阅读不满足可观测要求。
