# 项目文档最佳实践

本文定义每个工程必须具备的项目文档集合、各文档的边界与书写规则。共享工程标准通过工程 `AGENTS.md` 的托管块路由到这些文档；项目规约可以补充或收紧，但不得改变文档集合与边界语义。

## 必备文档

- 每个工程必须在根目录提供 `README.md` 和 `docs/RESPONSIBILITIES.md`。
- 业务（领域）服务还必须提供 `docs/DOMAIN.md`；拥有真实领域的基础设施工程也应提供，纯类库工程不需要。
- 三份文档是下限而不是全集；关键的基础设施能力或外部依赖可单独作为权威文档，由项目文档入口路由，文档名不宜过长。

## 文档边界

三份文档各回答一个问题，内容不得互相渗透：

- `README.md` 是工程地图，回答"这是什么工程、怎么构建运行与验证、模块在哪里、去哪里读更多"。它只承载范围概述、模块地图、验证命令和文档路由，不写职责哲学、不写领域规则；能力交付状态只保留一句概览并链接到 `docs/RESPONSIBILITIES.md`。
- `docs/RESPONSIBILITIES.md` 是服务章程，回答"本工程负责什么、不负责什么、与谁以什么契约协作、交付到什么程度"。不负责的条目必须标注所有者；它是跨服务协作契约的唯一归属地。
- `docs/DOMAIN.md` 是领域设计，回答"领域如何建模"。它承载统一语言、领域模型、不变量、用例、领域事件与错误和分层；不写部署与运行配置、不写交付状态、不写其他服务的职责。

## 跨服务协作契约

- 一个跨服务契约由调用方与被调方各自书写自己的那一半：调用方持有完整流程描述，被调方持有端点契约与自身消费语义。
- 双方各自在自己工程的 `docs/RESPONSIBILITIES.md` 中书写并互相链接，禁止在两个仓库重复维护同一张契约表或同一段流程。
- 契约变更时两侧同步更新，并以对方文档为链接目标而不是复制其内容。
