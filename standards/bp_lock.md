# 分布式锁最佳实践

本文基于 `framework-lock` 和 `framework-starter-lock-redis`，定义跨进程互斥、锁键、超时和数据一致性约束。

## 分布式锁

分布式锁用于需要跨实例串行化的竞争资源。并发数据写入采用的锁与数据库约束组合遵循[数据持久化最佳实践](bp_persistence.md#并发写与事务)。
- **强制 · 主题**：分布式锁不得作为唯一正确性保证；必须正确处理锁过期、进程暂停、网络分区和重复执行，并配合上文的并发写与事务约束提供独立的正确性保护。
- **强制 · 主题**：统一注入 `LockExecutor`，通过 `LockContext(waitTime, lockNames)` 执行临界区；业务代码不得直接依赖 Redisson、Spring Integration Redis Lock 或自行操作 Redis 锁命令。
- **强制 · 主题**：`lockNames` 必须构成同一竞争资源的稳定业务唯一键，不得使用随机值，也不得让同一资源出现多种键格式。
- **强制 · 主题**：`LockExecutor` 内部基于 `ResourceNameResolver` 完成键段规范化拼接（`String.join`）与命名空间注入；业务代码直接传入业务键段，不得额外解析或拼接资源键。
- **强制 · 主题**：`lockNames` 不得包含敏感数据，定义见[日志与敏感数据最佳实践](bp_logging.md#日志与敏感数据)。
- **强制 · 主题**：等待时间必须有界并按业务 SLA 配置，不得无限等待或在循环中无退避抢锁。
- **默认 · 主题**：获取锁默认优先立即尝试。
- **强制 · 主题**：获取锁失败必须返回明确的可重试、冲突或降级结果。
- **强制 · 主题**：租约必须覆盖正常临界区上界并留出安全余量；启用自动续租时仍须限制临界区时长。
- **强制 · 主题**：临界区应只包含必要的读改写，不执行可避免的远程调用、大批量处理或长事务。
- **强制 · 主题**：只允许持有锁的执行流在 `finally` 中解锁；必须使用 `LockExecutor` 的托管执行保证释放，不得跨线程移交锁所有权。
- **强制 · 主题**：锁保护数据库事务时，必须先获取锁，再开启受保护事务，并等待提交或回滚完成后释放锁；不得把事务内方法返回等同于事务完成，存在外层事务或代理时必须验证实际边界。
- **强制 · 主题**：多把锁必须定义并统一获取顺序；能通过一个聚合或业务唯一键收敛时不得获取多把锁，避免死锁和锁粒度扩大。

## 验证

- **强制 · 主题**：冒烟阶段的集成测试必须使用真实 Redis 覆盖互斥、获取失败、异常释放、租约/续租和 namespace 隔离。
- **强制 · 主题**：冒烟阶段的并发写测试必须同时证明只有一个业务结果生效且数据库唯一约束可阻止绕过锁的重复写入。
