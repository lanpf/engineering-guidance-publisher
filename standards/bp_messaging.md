# 消息中间件最佳实践

本文基于 `framework-message`、RabbitMQ starter 和可靠 outbox，定义事件发布、分区、消费、延迟及失败恢复约束。

## 事件与发布

- application 只能通过 `IntegrationEventOutbox` 提交集成事件，不得直接依赖 RabbitMQ template 或具体 broker API。
- 数据状态和 outbox 记录必须在同一本地事务提交；发布信号只能在事务提交后触发。不得使用直接发送替代需要可靠性的 outbox。
- 集成事件是服务间稳定契约，必须有全局唯一事件 ID、事件类型、聚合类型、聚合 ID 和发生时间；不得直接序列化领域实体或复用领域事件类型。
- 同一 outbox 批次只能包含同一聚合的事件，并保持批次序号；跨聚合事件必须拆分，不能宣称跨聚合全局顺序。
- 事件契约必须向后兼容演进；新增字段提供兼容默认语义，删除、改名或改变字段含义必须走版本迁移。

## 分区与顺序

- 需要同一聚合有序时使用稳定的聚合 ID 作为 `PartitionedOperations` 分区键；不得使用随机键或易变属性，也不得依赖全局顺序。
- destination、分区数、权重和路由算法必须集中配置并在启动时校验；不得在业务代码动态创建未治理的 destination。
- 调整分区数或路由算法前必须评估在途消息和顺序影响，并制定迁移方案。

## 消费与可靠性

- 消费者必须按至少一次投递设计，使用事件 ID 或稳定业务幂等键去重；不得假设 broker、outbox 或 listener 只投递一次。
- 只有业务处理和本地事务成功后才确认消息；失败必须按分类执行有界重试和退避，不可恢复或超过阈值的消息进入死信或人工处置链路。
- listener 只负责反序列化、校验、幂等入口和调用 application，不实现领域规则；不得吞掉异常后确认消息。
- 必须监控发布确认/退回、outbox 积压、重试次数、消费延迟和死信数量，并用 event ID、aggregate ID、destination 建立可追踪上下文。

## 延迟消息

- 延迟消息只用于可容忍误差的重试、提醒和辅助流程，不得作为精确定时器或核心业务截止时间的唯一保证。
- 使用 `DelayedOperations` 并明确每条消息的延迟；不得在业务代码直接依赖 RabbitMQ 延迟拓扑细节。
- 需要至少一次延迟投递时必须使用支持该语义的 quorum 配置；延迟层级、tick 和最大 TTL 必须在支持范围内并启动校验。
- 延迟消息到达后仍必须执行状态检查和幂等校验，过期或已完成业务不得产生重复副作用。

## 验证

- 使用真实 broker 的集成测试覆盖提交后发布、发布失败重试、重复投递、同聚合顺序、死信和延迟误差范围。
- 故障演练必须覆盖数据库提交后 broker 暂不可用、消费者处理中断以及恢复后的积压清理。
