# 通用工程规约

本文定义所有工程共同遵守的 Java、依赖、工具和测试约束。特定工程可以通过自己的内部规约补充或收紧本文，但不得放宽或覆盖本文。

## 规约引用

- 每个工程的文档必须声明当前采用的规约版本，以及工作区 `~/docs/standards/blob/<版本>/` 下规约文件的相对路径。
- 工程只从本地约定路径读取所继承的规约；构建前必须通过统一的构建工具插件校验全部所需规约可读，插件校验不通过时不允许构建。

## 规约变更与发布

- 本规约按版本发布，版本号发布后内容不可变更；任何调整须发布新版本，不得就地修改已发布版本的内容；每次发布须在变更记录中列出新增、修改和废止的条款及其生效版本。
- 收紧型变更（新增约束、缩小允许范围）可直接发布；放宽型变更须在发布说明中评估对已有工程的兼容性影响。
- 新版本发布后，已引用旧版本的工程可以按自身节奏升级，但新建工程必须引用最新版本。

## Java 语言

- **版本**
  - 使用 Java 17。

- **现代 Java 编程风格**
  - 能够在构造时完整确定状态、构造后不再变化，且不依赖继承、代理或 JavaBean setter 绑定的数据载体优先使用 Java `record`；集合组件须通过 `List.copyOf`、`Set.copyOf` 等方式防御性复制。需要继承、可变状态、框架代理或 JavaBean 形态时使用普通类。
  - 简单集合遍历优先使用 `forEach`，简单转换、过滤和映射优先使用 `Stream`，简单回调逻辑优先使用 lambda 和 method reference。
  - 可能缺失的返回值及其链式处理优先使用 `Optional`，不将 `Optional` 用作 Bean 属性或方法参数。
  - 复杂业务逻辑、嵌套条件和异常流程以可读性优先，不强制使用函数式写法。

- **基础工具类**
  - 不重复造轮子：通用技术能力优先使用 JDK、当前工程已依赖的框架，或社区成熟且持续维护的库；散列、编码、集合扩展、I/O 等通用能力优先评估并使用 Guava、Apache Commons 等成熟库，不自行实现已有可靠实现的底层算法和基础设施代码。
  - 模块内已依赖 Spring Framework 时，字符串、集合等通用处理优先使用 `StringUtils`、`CollectionUtils` 等 Spring 工具类，避免重复实现判空、字符串处理和集合判断等基础工具逻辑。
  - 引入新的成熟库时应评估维护活跃度、安全性、许可证和依赖成本，并统一版本；已有依赖能够满足需求时不重复引入功能重叠的库。

- **类型选择**
  - 优先使用 `Integer`、`Long`、`Boolean` 等包装类型，仅在明确需要基本类型默认值、性能特性，或语义上不允许为空时使用基本类型。

- **参数校验**
  - 优先使用 Bean Validation（Jakarta Validation）表达可校验、可绑定的 Bean 属性和方法参数约束。
  - 仅在框架校验无法覆盖，或内部 API 需要快速失败时使用 `Assert` 等显式参数检查。

- **异常表达**
  - 优先使用框架提供的异常体系表达框架层、参数绑定层和校验层异常；业务不变性、领域规则或业务约束使用明确的领域异常表达，不使用通用运行时异常替代。
  - 业务异常统一归属明确的异常基类/错误码体系，不允许抛出未分类的通用运行时异常表达业务语义。
  - 业务异常必须处理或抛出，非业务异常必须记录日志，不允许静默忽略；异常需携带足以定位问题的上下文信息。

## 依赖规范

- 每个 module 只声明当前编译和运行语义必需的最小依赖，不因潜在使用场景提前引入依赖。
- module 之间禁止循环依赖；出现循环依赖须通过抽取公共 module 或调整职责边界消除，不允许通过反射、事件等方式绕开编译期循环依赖检查。
- 只有承载具体技术实现、运行时适配或最终打包装配的 module 才可以引入聚合型 starter；其余 module 优先依赖最小能力包。
- 依赖 scope 须与实际用途匹配：编译期必需的依赖使用 `compile`；仅测试代码使用的依赖使用 `test`，不得泄漏到主代码路径；`provided`、`optional` 仅在依赖确由运行环境提供或功能确属可选时使用，不得用于回避依赖声明。
- SNAPSHOT 版本依赖不得出现在发布分支和生产构建中，仅允许在本地开发或未发布的迭代分支中临时使用。
- 已由运行框架自动提供的基础设施 Bean 应通过注入复用，不重复声明同语义 Bean。
- 三方依赖版本通过统一 dependency management 管理，业务和功能 module 不单独覆盖版本。

## 工具规范

### Lombok

**通用原则**
- 不使用 `lombok.experimental` 包下的实验性注解。
- 不使用 `@Builder`；需要分步或链式构造对象时显式编写构造函数或工厂方法。
- 对不适合使用 `record` 的类，使用 Lombok 简化访问器和构造器等样板代码：仅按字段赋值、无需校验或转换逻辑的构造器，优先使用 `@NoArgsConstructor`、`@AllArgsConstructor` 或 `@RequiredArgsConstructor`（不限于 Spring Bean）；构造过程包含不变性校验、参数转换或其他初始化逻辑时，显式编写构造函数。
- 需要日志时使用 `@Slf4j`，不手写 `Logger` 字段。

**按类型约定**
- 领域实体、聚合根：仅使用 `@Getter`，状态变更通过领域行为完成；不使用 `@EqualsAndHashCode`（含 `@Data`），相等性基于唯一标识显式实现 `equals`/`hashCode`。
- 值对象：优先使用 Java `record`；不适合时使用 `final` 字段 + `@Getter` + `@AllArgsConstructor` 保持不可变（是否显式编写构造函数按通用原则处理），可使用 `@EqualsAndHashCode` 按全部字段判断相等性。
- Spring Bean：使用 `final` 字段 + `@RequiredArgsConstructor` 做构造器注入（是否显式编写构造函数按通用原则处理）。

### MapStruct

**基本原则**
- 使用 MapStruct 进行对象转换，不手写字段搬运逻辑，不使用 `BeanUtils.copyProperties` 复制对象。

**契约与实现分离**
- MapStruct 只作为转换器接口的实现方式，不直接承担转换器契约定义。
- 实现放在契约所在包的 `mapstruct` 子包，类名统一为 `*MapStructMapper`，通过 `@Mapper` 实现契约接口，并使用 `@Override` 实现契约方法。

**组合复用**
- 多个 Mapper 之间存在可复用的转换逻辑时，优先通过 `@Mapper(uses = {...})` 组合已有 Mapper，不在多个 Mapper 中重复实现相同的字段级转换逻辑。

**公共配置**
- `componentModel = spring` 和 `unmappedTargetPolicy = IGNORE` 在公共 `@MapperConfig` 中声明，各 Mapper 通过 `config` 引用，不重复声明。

**辅助转换器**
- 通用 converter 作为 mapper 的 helper，仅供 mapper 引用，不向业务组件开放。

## 测试规范

- **测试边界**
  - 单元测试和模块内契约测试保留在被测 module 的 `src/test` 中，就近验证类行为、模块协作和配置边界。
  - 跨 module、完整自动装配或依赖真实中间件、数据库等基础设施的测试定义为集成测试，不放入生产 module。
  - 测试验证可观察行为和公共契约，不依赖非必要实现细节；真实基础设施场景优先使用 Testcontainers 提供隔离且可重复的运行环境。
  - 单元测试中仅对被测对象的外部协作对象（依赖注入的 collaborator）使用 Mock；禁止对被测对象本身做部分 Mock（partial mock/spy 替换被测逻辑），避免验证结果偏离真实行为。

- **结构与复用**
  - 集成测试类保持场景自包含，容器、测试应用、配置、探针和生命周期管理优先放在对应 `*IT` 中。
  - 仅在多个测试存在稳定且有意义的复用时抽取测试支持代码，不为减少少量重复建立通用测试基类。

- **文档与观测**
  - 每个集成测试必须提供同名测试文档，说明测试目标、运行条件、执行方式、手工观测步骤、观察入口和预期结果。
  - 独立测试 module 的根目录 `README.md` 只说明覆盖范围、环境要求、统一执行方式、报告位置和文档索引；详细说明放在 `docs/<测试类名>.md`。
  - 集成测试必须可手工观测关键过程和最终结果；仅依赖自动断言或阅读实现代码不满足手工可观测要求。

- **生命周期与命名**
  - 单元测试和模块内契约测试使用 `*Test`，由 Maven Surefire 在 `test` 阶段执行。
  - 集成测试使用 `*IT`，由 Maven Failsafe 在 `integration-test` 和 `verify` 阶段执行。
  - 测试方法使用 `should<ExpectedBehavior>` 命名，直接表达被验证的可观察行为。
  - 外部基础设施优先通过 `@Testcontainers` 和 `@Container` 管理；测试创建的应用上下文及执行器在 `@AfterEach` 中释放。
