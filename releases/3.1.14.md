# 3.1.14

## 范围

基于已发布 3.1.13，明确泛型信封的集合所有权边界及 Commons Lang 基础工具准入、Guava 能力边界，移除已删除 Require 批量断言 API 的使用规则，并定义业务契约与技术防御的分流、NPE 禁令、技术诊断消息及最新 Require / NullSafe 的使用契约；不修改既有发布标签或历史规则记录。

## 政策变更

- 新增 `JAVA-GENERIC-ENVELOPE-OWNERSHIP-001`（required / baseline）：明确不接管 payload 所有权的泛型信封保持引用透明，不猜测运行时类型或强转复制；公开契约不承诺快照或深层不可变，调用方负责 payload 契约要求的隔离及发布期间稳定性。
- 修订 `JAVA-COLLECTION-OWNERSHIP-001`，引用该有限例外；这是对适用范围的放宽，不是所有 API 类型的豁免。集合所有者及 `PageResult`、`PagedList` 仍在保存边界复制容器。
- 不要求任意泛型 payload 一律不可变，不改变已有集合复制可变性和元素隔离规则。

- 新增 `DEP-COMMONS-LANG3-BASELINE-001`（default / baseline）：framework 工程优先采用统一管理的 commons-lang3，实际使用的 module 直接声明；仅管理版本或偶然传递引入不等于模块依赖，JDK 足够时无需无条件引入。
- 新增 `JAVA-UTILITY-GUAVA-SCOPE-001`（required / baseline）：Guava 因哈希等特定能力按需引入，不因其附带 Preconditions 就替代优先的校验工具。
- 修订 `DEP-OVERLAP-001` 与 `JAVA-VALIDATION-003`（均 required / baseline）：按实际能力判断重叠，允许使用统一 Commons Lang 基线，仍禁止随意新增检查工具依赖。

## Consumer 与发布状态

develop-service 的 java-language.md、dependency-rules.md、common-utilities.md、validation.md、service-validation.md、error-codes.md 和 infrastructure-interfaces-boot.md 变化清单见 3.1.14.rules.json；补充依赖 Scope 与版本章节的精确 source；Skill 路由、blueprint 和 scope 不变。下述新增、修订及退役均以已发布 3.1.13 为基线，保留全部旧文本与替代关系。

## Require 批量断言移除（2026-11-04）

- 退役 `JAVA-REQUIRE-NONNULL-BATCH-001`，移除多个参数必须使用批量方法及禁止连续调用 `notNull` 的约束，不再要求使用已删除的方法；完整旧文本及分类保留在本版本规则记录。
- 修订 `JAVA-REQUIRE-NONNULL-SCOPE-001`，按后续确认的失败语义分流：业务非空守卫使用业务异常供应器，不再限制其变量位置；普通技术防御不得使用该方法。
- 批量规则清理时仅评审 errorMessage 的新用法；随后按用户确认补充下述规范。

## 技术诊断消息（2026-11-04）

- 新增 `JAVA-CHECK-ERROR-MESSAGE-001`（default / baseline）：技术检查优先提供显式诊断消息；默认消息仅在统一封装已提供等价诊断上下文等具体理由下使用，失败语义仍优先。NullSafe 最新 API 通过异常供应器而非 errorMessage 参数指定元素异常。
- 新增 `JAVA-CHECK-DIAGNOSTIC-CONTENT-001`（required / baseline）：显式诊断消息非空白，指出被检查对象和违反的约束，不使用缺少上下文的泛化文案，不包含敏感原始值。
- 新增 `JAVA-NULLSAFE-EXCEPTION-SCOPE-001`（required / topic）：异常供应器只处理元素及 Map key/value 的非空检查，不拒绝 null 容器；业务检查必须提供业务异常供应器。它替换草稿中尚未发布、对应旧 API 的 `JAVA-NULLSAFE-ERROR-MESSAGE-SCOPE-001`，不改变任何已发布 ID。
- 修订 `JAVA-VALIDATION-REQUIRE-001`，明确禁止用通用 FrameworkException 加业务文案替代业务异常。
- 修订 `JAVA-EXCEPTION-LANGUAGE-001`，明确 FrameworkError 等框架通用技术错误的默认消息使用英文，服务业务错误仍使用中文模板。
- 修订 `ERROR-MESSAGE-TEMPLATE-001`，稳定模板约束服务自定义错误码，框架通用技术断言的可定制诊断不冒充业务协议。

framework 工程按本次明确授权将 FrameworkError 默认消息翻译为英文并更新测试及公开契约说明；枚举名称、本地码和完整码不变。这是相邻工程的本地代码修改，不代表该工程构件或本规范已发布；不包含 noNulls 默认错误码的额外调整。

## 业务守卫、技术防御与 NPE 边界（2026-11-04）

- 新增 `JAVA-BUSINESS-CHECK-TOOL-001`（required / baseline）：按业务约束及可读性选择 Require 的业务异常供应器或显式业务守卫，不要求将业务守卫机械改成工具调用。
- 新增 `JAVA-DEFENSIVE-CHECK-TOOL-001`（required / baseline）：纯技术防御按已有依赖选择语义匹配的 Assert 或 Validate；Spring module 优先 Assert，Spring 解耦 module 使用 Validate。只有可用工具无法满足时才编写通用技术守卫；不为校验引入 Spring。
- 新增 `JAVA-VALIDATION-NPE-001`（required / baseline）：禁止主动抛 NPE、使用 NPE 型预期校验或依赖隐式解引用；禁止用 Objects.requireNonNull、Validate.notNull 校验。对可预见的 null 在调用前按契约拒绝或归一化；不禁止已保证非 null 后正常使用 JDK API。
- 新增 `JAVA-NPE-DEFECT-001`（required / baseline）：意外 NPE 是程序缺陷，不统一包装为预期业务拒绝；统一系统失败边界不改变缺陷分类。
- 新增 `JAVA-REQUIRE-COLLECTION-BUSINESS-GUARD-001`（default / topic）：集合元素或 Map key/value 非空确为业务契约时，优先使用 Require.noNulls 的业务异常供应器；技术完整性检查不因此变成业务拒绝。
- 退役 `JAVA-CHECK-TOOL-ORDER-001` 和 `JAVA-REQUIRE-NO-NULLS-SELECTION-001`，不复用 ID；旧的单链工具优先级和技术检查优先 Require 规则分别由上述业务、技术分支接替。
- 修订技术前置条件、业务检查范围、Require.notNull 语义范围、集合异常选择、NullSafe 用途、异常语义分类和通用工具引用，消除与新分流的冲突。业务构造器、public 业务入口和关键流程中的业务契约失败使用业务异常；缺失注入依赖及内部程序不变量仍为技术失败，不能仅按方法可见性或变量位置分类。
- Commons Validate.notBlank、notEmpty 等方法在 null 输入时可能抛 NPE，只有已建立非 null 前提时才使用它们检查其他约束。布尔 null 判定 Objects.isNull/nonNull 不属于 NPE 型校验；Bean Validation 的字段形态校验优先政策保持不变，执行机制与异常边界按下述确认方案修正。

本轮仅更新本发布器的政策、catalog 和草稿记录，不修改 framework 或其他 consumer 工程，不运行或实施 consumer 重构。

## 显式检查精简与最新 API 对齐（2026-11-05）

- 将正文按失败语义与工具、诊断与 null 防御、Require、NullSafe 和责任边界组织，拆开混合规则，移除条目序号引用；异常分类只在显式检查中维护，保留 `JAVA-EXCEPTION-SEMANTICS-001` 的 ID 及基础级别。
- `JAVA-REQUIRE-NONNULL-SCOPE-001` 放宽业务守卫的位置限制；普通技术防御仍按 Assert / Validate 规则执行。显式消息偏好为 default，消息内容及 NPE 禁令仍为 required。
- 保留 `JAVA-REQUIRE-VALID-PURITY-001` 与 `JAVA-CROSS-VARIABLE-GUARD-001` 的 ID，更新到 `Require.satisfies`，明确无副作用、不可变常量和跨变量判断边界。
- 新增 `JAVA-REQUIRE-COLLECTION-CONTRACT-001`（required / topic）：区分 notEmpty、noNulls 和两种 noDuplicates 的检查范围、空容器语义、供应器覆盖范围及可变返回结果。
- 新增 `JAVA-COLLECTION-DUPLICATE-REJECTION-001`（required / topic）：业务拒绝重复项时不得以静默去重替代唯一性检查。
- 新增 `JAVA-VALIDATION-CALLBACK-EXCEPTION-001`（required / topic）：异常供应器不转换谓词、keyMapper 或 consumer 自身的异常。
- 新增 `JAVA-NULLSAFE-CALLBACK-CONTRACT-001`（required / topic）：visit 必须提供非 null consumer，复制方法可省略；null 容器跳过或归一为空，不调用元素异常供应器。
- 修订 `JAVA-NULLSAFE-COPY-SELECTION-001`，反映业务异常供应器、不可变浅拷贝、保序变体及 Set 去重；保留 null 与空语义等价的适用门槛，不重复元素非空检查。

上述修改在发布前合并到同一个 3.1.14 草稿，没有单独发布中间版本；blueprint、Skill 路由与 scope 不变。

## Bean Validation 与异常边界（2026-11-05）

- 新增 `JAVA-BEAN-VALIDATION-NULLABILITY-001`、`JAVA-BEAN-VALIDATION-CONTAINER-001`（均 required / baseline）：明确注解对 null 的不同语义，以及容器约束、元素约束和元素级联的独立职责。
- 将重复的入口组选择规则合并到 `JAVA-MVC-OBJECT-VALIDATION-001`，仅适用于 MVC 请求对象的参数级绑定校验；退役 `JAVA-VALIDATION-ENTRY-GROUP-001`，在规则记录中保留完整旧文本及替代关系。
- 新增 `JAVA-METHOD-VALIDATION-GROUP-001`（required / topic），区分普通 Bean 与 MVC 内置方法校验的分组位置；对象级联仍使用 @Valid，不能以参数上的 @Validated 替代。普通 Bean 的类级启用及代理调用规则保持不变。
- 修订 `JAVA-VALIDATION-CONTRACT-002`，覆盖继承或实现方法的参数约束与参数级联标记，不将参数约束禁令套用于返回值约束；修订 `JAVA-MVC-METHOD-VALIDATION-001`，明确直接参数或返回值约束采用 MVC 内置方法校验。
- 修订 `JAVA-BEAN-VALIDATION-EXCEPTION-001`，按来源区分外部入参错误、返回值契约违约及约束或校验器配置错误；后两类按服务端缺陷处理，统一响应契约不要求先重抛框架异常。
- `JAVA-BUSINESS-EXCEPTION-BASE-001` 作为业务异常基类的唯一权威声明保留；`JAVA-VALIDATION-REQUIRE-001` 维护业务拒绝语义并引用异常体系，`JAVA-DOMAIN-GUARD-001` 只维护领域守卫的特殊要求。
- 修订 `JAVA-EXCEPTION-LANGUAGE-001`，技术诊断与 Bean Validation 提示的英文要求由本文件维护，业务中文模板与稳定性引用错误码文档；`JAVA-EXCEPTION-003` 精简为按契约处理、转换或传播，禁止静默吞异常。
- 修订 `INTERFACES-REST-CONTEXT-001`，HTTP Request 保持可变类型及 ClientRequest 继承要求，具体校验注解回引校验规范，不再由分层文档写死 @Valid。

上述修改继续合并到同一个 3.1.14 草稿，不修改 consumer 代码、Skill blueprint、路由或 scope。
